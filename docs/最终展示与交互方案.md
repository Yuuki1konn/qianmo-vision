# 最终展示与交互方案

## 1. 展示目标

本项目面向农村二轮车出行辅助场景，界面与交互必须满足三个原则：

- 简洁明了
- 语音提示直接、易懂
- 推理稳定，不出现明显卡顿和跟不上画面的情况

考虑到老年用户比例较高，系统不应依赖复杂图标或大量文字说明，而应以“大区域提示 + 少量状态字 + 中文语音”作为核心交互方式。

## 2. 最终模型展示建议

### 2.1 分割模型展示

- 主显示模型：
  - 使用 `relaxed` 分割模型
  - 输出更符合人对“当前道路与可换道区域”的直觉
- 辅助安全边界：
  - 保留 `strict` 模型作为安全边界参考
  - 但默认不直接展示给普通用户

### 2.2 画面呈现方式

推荐采用“三层叠加”：

- 底层：原始相机画面
- 中层：半透明道路可行驶区域
- 上层：检测框与少量中文标签

建议颜色：

- 主可行驶区域：青绿色或绿色半透明
- 高风险目标框：红色
- 中风险目标框：黄色
- 普通目标框：白色或浅绿色

不建议：

- 在画面中堆太多类别名称
- 同时显示太多数字
- 做复杂导航箭头或密集图标

## 3. 推荐界面布局

### 3.1 主界面

主界面只保留 4 类信息：

- 相机实时画面
- 当前道路可行驶区域
- 关键危险目标提示
- 当前系统状态

### 3.2 顶部状态栏

顶部只显示：

- 当前模式：`识别中`
- 当前速度状态：`流畅 / 一般 / 降级`
- 语音状态：`语音开 / 语音关`

### 3.3 底部状态栏

底部建议只显示一句中文状态：

- `前方道路正常`
- `前方有行人`
- `前方有坑洼`
- `靠近道路边缘`
- `前方可行驶区域变窄`

不要在底部堆多行文字。

## 4. 中文语音提醒方案

语音提醒要遵守两个原则：

- 说人话
- 不重复轰炸

### 4.1 基本提醒等级

#### 正常状态

- 默认不播报，避免干扰

#### 提醒级

适用于：

- 前方出现行人
- 前方出现动物
- 前方出现坑洼
- 前方道路变窄

推荐文案：

- `前方有行人，请注意`
- `前方有动物，请减速`
- `前方有坑洼，请避让`
- `前方道路变窄，请小心通行`

#### 警告级

适用于：

- 障碍物距离近
- 偏离可行驶区域明显
- 前方可行驶区域急剧收缩

推荐文案：

- `注意，前方障碍物较近`
- `请回到道路中间`
- `前方通行空间不足，请减速`

### 4.2 不同情况的提醒策略

建议按场景拆分：

- 行人：
  - 只在接近中心区域、且距离较近时播报
- 动物：
  - 一旦检测稳定，就优先播报
- 坑洼：
  - 当位于当前可行驶区域中央或前进方向时播报
- 路障：
  - 仅在前方主通行方向上时播报
- 偏离道路：
  - 连续数帧都检测到偏离，才播报

### 4.3 语音节流策略

必须做节流，否则体验会很差。

建议规则：

- 同类提醒至少间隔 `3~5 秒`
- 更高优先级提醒可打断低优先级提醒
- 同一句话不要连续播两次

推荐优先级：

- `偏离道路 / 障碍物过近`
- `动物 / 行人`
- `坑洼 / 路障`
- `道路变窄`

## 5. 性能目标

### 5.1 体验目标

端侧推理不能追求“绝对最高精度”，而应优先满足：

- 画面连续
- 延迟稳定
- 提醒及时

对于农村二轮车辅助场景，推荐目标：

- 感知刷新率：`>= 12 FPS`
- 理想目标：`15~20 FPS`
- 单帧总时延尽量控制在：`80ms ~ 150ms`

如果低于 `10 FPS`，用户会明显感觉到延迟和“跟不上”。

### 5.2 不能出现的情况

以下情况必须尽量避免：

- 语义掩码明显滞后于相机画面
- 检测框一跳一跳、忽隐忽现
- 系统因一帧过慢而长时间卡住
- 语音提醒晚于危险出现太久

## 6. 端侧性能策略

### 6.1 推理节奏

不要每一帧都做全量推理，建议采用异步流水线：

- 相机线程持续采集
- 推理线程始终只处理“最新一帧”
- 渲染线程显示“最近一次有效结果”

这样即使偶发慢帧，也不会整条链路卡住。

### 6.2 结果更新策略

建议：

- 分割结果允许以较低频率更新，例如 `10~15 FPS`
- 检测结果允许与分割错帧融合
- 渲染层始终按屏幕刷新显示最近结果

### 6.3 轻量后处理

分割后建议保留少量后处理：

- 小区域去噪
- 闭运算补断裂
- 时间平滑

但不要做过重的 CPU 后处理，否则会拖慢整体速度。

### 6.4 建议的端侧模型使用方式

- 默认使用 `relaxed` 分割模型作为可行驶区域主输出
- 保守版 `strict` 不一定需要同时实时跑
- 若端侧算力有限，可以只部署 `relaxed`
- `strict` 可保留为离线分析或备用模型

## 7. 最终推荐方案

### 7.1 主显示

- 主显示使用 `relaxed` 分割模型
- 配合检测模型显示关键风险目标

### 7.2 语音

- 默认语音开启
- 仅播报高价值信息
- 强制做同类提醒节流

### 7.3 性能

- 目标至少 `12 FPS`
- 采用异步最新帧策略
- 遇到性能不足时，优先降低：
  - 渲染分辨率
  - 分割刷新频率
  - 检测刷新频率

而不是让整体界面卡死

## 8. 当前项目建议下一步

- 先导出主分割模型 `relaxed`
- 设计简洁中文界面原型
- 设计语音提醒规则表
- 在真机上做一次端侧性能验证

## 9. 当前落地默认选择

- 主显示模型：
  - `relaxed`
- 主部署格式：
  - `FP16 TFLite`
- 备用部署格式：
  - `Dynamic Range Quantization TFLite`

原因：

- `relaxed` 更符合道路直觉
- `FP16` 更接近训练输出
- 若性能不足，再切换到动态范围量化版本
