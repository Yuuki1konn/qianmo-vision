# 端侧落地影响与下一步建议

## 1. 结论先说

当前最适合落地到最终应用的组合是：

- 分割主模型：`relaxed`
- 分割部署格式：`FP16 TFLite`
- 检测模型：保持当前最佳检测源权重，等待部署导出打通
- `strict` 模型：不作为默认实时输出，只作为安全参考

原因很直接：

- `relaxed` 的道路区域更符合人的直觉，展示效果明显更自然。
- `FP16 TFLite` 已完成一致性验证，输出更接近训练时模型。
- `Dynamic Range Quantization` 可以更快，但边界细节和稳定性通常会略差一点。

## 2. 不同落地模型对最终结果的影响

### 2.1 `relaxed` vs `strict`

`relaxed` 的影响：

- 道路区域更连贯
- 可换道区域更容易被保留下来
- 界面观感更自然
- 更适合作为用户看到的主结果

`strict` 的影响：

- 输出更保守
- 更容易出现道路收缩
- 对“宁可少给、不要多给”的安全边界有意义
- 不适合直接作为唯一主显示结果

对最终应用的实际意义：

- 如果主界面用 `strict`，用户会更容易觉得“系统只认一小块路”。
- 如果主界面用 `relaxed`，更接近日常骑行直觉，也更容易被接受。

### 2.2 `FP16 TFLite` vs `Dynamic Range Quantization TFLite`

`FP16 TFLite` 的影响：

- 更接近原始模型输出
- 边界细节保留更好
- 更适合主显示
- 文件比量化版大

`Dynamic Range Quantization TFLite` 的影响：

- 模型体积更小
- CPU 推理通常更轻一些
- 掩码边缘、细碎区域可能会更粗
- 更适合性能不足时的备选方案

对最终应用的实际意义：

- 如果真机能稳定跑动，优先上 `FP16`
- 如果真机明显掉帧，再切换到 `Dynamic Range`

## 3. 对最终界面的直接影响

### 3.1 用户真正会看到什么

模型不同，用户最直接看到的是：

- 绿色可行驶区域是否自然
- 是否容易断裂
- 语音提醒是否过于频繁
- 画面是否滞后

真正影响体验的不是单一指标，而是三件事：

- 掩码是否像“路”
- 提醒是否像“人话”
- 画面是否跟得上

### 3.2 当前推荐的主显示方式

- 主可行驶区域：使用 `relaxed + FP16`
- 风险目标框：使用检测模型
- 普通用户默认不显示 `strict`

只有在以下情况，才考虑引入 `strict`：

- 做开发调试界面
- 做安全参考边界对比
- 离线分析误判

## 4. 对语音提醒的影响

模型更宽松后，语音策略必须更保守，避免误报过多。

建议：

- 分割结果本身不直接播报“道路很宽”
- 分割只用于支持以下提醒：
  - `靠近道路边缘`
  - `前方可行驶区域变窄`
  - `请回到道路中间`

检测结果用于支持以下提醒：

- `前方有行人，请注意`
- `前方有动物，请减速`
- `前方有坑洼，请避让`
- `注意，前方障碍物较近`

这样做的好处是：

- 分割负责“路在哪里”
- 检测负责“危险是什么”
- 语音更稳定，不容易乱说

## 5. 对性能的影响

### 5.1 不能接受的情况

- 掩码比相机画面慢很多
- 识别结果一帧有一帧没有
- 语音延后太久
- 系统因为推理堵塞而卡住

### 5.2 推荐性能策略

- 分割和检测都不要逐帧排队
- 始终只处理最新一帧
- 分割允许低频更新
- 检测允许与分割错帧融合
- 渲染线程永远不能被推理阻塞

### 5.3 当前推荐目标

- 最低目标：`12 FPS`
- 较舒适目标：`15~20 FPS`
- 若低于 `10 FPS`，优先降级，而不是硬撑

降级顺序建议：

1. 降低渲染分辨率
2. 降低分割刷新频率
3. 切换到 `Dynamic Range` 分割模型
4. 再考虑降低检测刷新频率

## 6. 下一步建议

现在最合理的下一步不是再训模型，而是做应用侧的规则固化。

建议顺序：

1. 用 `relaxed + FP16` 作为主方案
2. 明确语音提醒规则表
3. 明确界面状态文案
4. 设计异步推理与降级策略
5. 真机测一次 FPS、延迟、发热
